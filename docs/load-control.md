# Opinet 기준 서버부하 억제

사용자 추가 지시에 따른 T006A 계약이다. 인증 Open API를 호출하거나 인증키를 저장하지 않는다.
공개 웹의 유사 기능만 구현하며, API 쿼터를 웹 데이터 호출 허가량으로 해석하지 않는다.

## 공통 전송 예산

참조는 로컬 `python-opinet-api/src/opinet/_ratelimit.py`, `_http.py`, `_httpx.py`와
`docs/async-tps.md`다. Opinet은 한 루프의 FIFO 버킷을 요청/재시도/redirect에 공유하고,
401/403/429에서 즉시 중단하며 검증 실패·캐시 적중에는 전송하지 않는다.
이를 Chromium의 실제 요청 전송 경계로 적용한다. Opinet HTTP transport 자체를 복사해
Chromium이라고 부르거나 인증키·인증 엔드포인트를 가져오지 않는다.

| 항목 | krits 계약 |
|---|---|
| 기본 전송률 | 5 RPS, capacity1. Opinet 기본 5 RPS를 참고하되 초기 burst를 1로 제한 |
| 적용 대상 | 허용된 ITS 문서·스크립트·스타일·XHR/fetch·각 redirect hop |
| 적용 위치 | CDP Fetch Request 단계에서 전송 직전 `await bucket.acquire()` |
| 공유 | `rate_limiter=AsyncTokenBucket(...)`를 여러 클라이언트에 같은 인스턴스로 주입 |
| 차단 자원 | 외부 origin·OpenAPI·타일·영상·이미지 등은 토큰 없이 차단 |
| 재시도 | 기본/현재 0회. 자동 반복으로 부하를 늘리지 않음. 401/403/429 즉시 오류 |
| timeout | 기본90초. lock과 실제 전송 토큰 대기 포함, 취소 후 자원 정리 시간 별도 |
| 루프 | 클라이언트/버킷 모두 한 이벤트 루프. 버킷 루프 불일치는 브라우저 시작 전 거부 |

기존 T002–T006의 1 RPS는 수집 operation 예약이었다. T006A부터 개별 전송 예산으로
변경됐으므로 과거 검증 문서의 숫자를 현재 계약으로 읽지 않는다. 허용 자산 수가 많은 초기
문서도 같은 버킷을 쓰며 기본 timeout을 90초로 둔다. 실제 서버의 허용량을 보장하는 설정이
아니다. 소비자는 필요하면 `AsyncTokenBucket(1, capacity=1)`처럼 더 낮춘다.

page 종료 전에 CDP listener를 제거하고, 이미 생성된 토큰 대기 task를 취소·회수한 뒤 page와
session을 닫는다. 취소된 대기 작업이 나중에 토큰을 가져가거나 닫힌 page에 전송하지 않는다.
네트워크를 쓰지 않는 잘못된 인자, 차단 자원, 캐시 적중에는 예산을 소모하지 않는다.

허용된 페이지 자산도 401/403/429이면 page를 닫아 즉시 추가 전송을 중단하고 해당 접근/제한
오류를 반환한다. 토큰 대기에서 깨어난 작업도 거부 상태를 다시 확인한다. idle 중 늦게 도착한
거부가 있으면 완료 캐시로 덮지 않고 다음 작업에서 오류와 정리를 수행한다. 사용자가 오류 후
새로 명시 호출하면 새 세션을 만들 수 있지만 라이브러리는 자동 재시도하지 않는다.

## 제한된 완료 캐시

교통/돌발/CCTV/우회/도시간/일반 파일·자료실 조회에 기본 `cache_ttl=15.0`초,
`cache_max_entries=32`의 클라이언트별 LRU를 둔다. 성공한 결과만 저장한다. 정상 빈 배열은
성공 결과이므로 캐시할 수 있지만 오류·취소·접근 제한은 저장하지 않는다.
`cache_ttl=0`은 완료 캐시를 끈다. 진단용 `get_page_snapshot`은 캐시하지 않는다.

기본 인자를 적용한 같은 메서드·같은 인자의 완료 값만 재사용한다. 파일 다운로드 bytes나
서비스 DB는 이 캐시의 대상이 아니다. 캐시 수명은 완료 시점의 monotonic clock으로 계산하고
반환 모델의 `collected_at`은 원래 실제 조회 시각을 보존한다. 캐시 적중에 수집 시각을 새로
만들어 최신 자료처럼 보이게 하지 않는다. TTL은 원문 제공 시각이나 데이터 유효기간이 아니다.

저장·반환 시 복사해 raw dict를 포함한 호출자 수정이 다른 결과에 섞이지 않도록 한다.
`client.clear_cache()`는 완료 값만 비우고 진행 중 요청은 취소하지 않는다. 비우기 이전에 시작한
요청이 늦게 끝나도 완료 캐시를 다시 채우지 않는다. 종료 시 모든 완료 값을 제거하며, 종료 후
캐시 값만 반환하는 재사용도 거부한다. 장기 저장·스케줄링은 소비자가 담당한다.

## 동일 진행 조회 공유

같은 클라이언트에서 같은 인자의 동시 요청은 실제 조회 task 하나를 공유한다. 완료 캐시를
꺼도 진행 중 요청 공유는 유지한다. 서로 다른 조건은 합치지 않으며 여러 클라이언트의 캐시는
서로 공유하지 않는다. 여러 클라이언트의 실제 전송 예산은 공통 버킷으로 공유할 수 있다.

한 대기자 취소는 다른 대기자의 조회를 취소하지 않는다. 마지막 대기자까지 취소하면 실제
조회 task를 취소하고 브라우저 자원 정리를 기다린다. 반복 취소에도 정리가 끝나기 전 반환하지
않는다. 실패는 같은 진행 요청의 대기자들에게 그대로 전달하며 내부에서 재시도하지 않는다.
취소·정리 중인 task는 신규 공유 대상에서 즉시 제외한다. 같은 키의 새 호출은 기존 정리가
끝난 뒤 별도 조회를 시작하며, 종료 시에는 공유 대상에서 빠진 정리 task도 모두 기다린다.
실패 후 사용자가 새로 호출하면 새로운 명시적 요청이다. 종료는 진행 조회 완료를 기다린 뒤
캐시와 소유 브라우저를 닫는다. 공유 task에는 원래 operation timeout 하나가 적용된다.
각 대기자의 timeout에는 공유 결과 대기와 이전 취소 정리 대기도 포함한다. 새 대기자가 시간
제한으로 끝나더라도, 이전 호출이 소유한 정리를 취소하거나 새 네트워크 요청을 시작하지 않는다.

## 실제 검증

기본 테스트는 네트워크 없이 TTL/LRU·만료·복사·기본 인자 정규화·실패 미보관·동시 공유·
한 명/마지막 대기자 취소·반복 취소·종료·캐시 비우기 세대를 검증한다.
실제 Chromium 로컬 서버에서 다음을 카운터와 monotonic 수신 시각으로 확인한다.

- 두 클라이언트가 공유하는 2 RPS/capacity1에서 문서/스크립트/데이터 전송 간격.
- 동시 동일 조회1회, 완료 캐시 적중 추가0회, 명시적 캐시 비우기 후 추가1회.
- 초기401/403/429를 동시 대기자가 공유하고 재시도/성공 캐시 없이1회로 중단.

실제 ITS 전체 live도 별도로 실행하며 로컬 카운터 테스트를 실제 ITS 데이터 검증으로 세지 않는다.
