# 적대적 리뷰와 단계별 머지

1. 소스·문서를 완성하고 Draft PR을 만든다. 대상 commit SHA와 task ID를 기록한다.
2. 서로 독립적인 **두 리뷰 에이전트**에게 동일 SHA를 읽도록 한다. 구현에 참여한 에이전트를
   자기 코드의 독립 리뷰어로 세지 않는다. 두 리뷰어는 서로의 결론을 보기 전에 별도 조사한다.
3. 리뷰 A는 요구사항/출처 근거/범위/파서/데이터 손실을, B는 자원 누수/취소/파일 손상/
   경로·크기 경계/테스트의 맹점을 확인한다. 문서 PR도 실행 가능한 수용 기준을 공격적으로 검토한다.
4. 지적은 우선순위·파일 위치·재현/근거·수정 요구를 포함한다. P0~P2는 수정하고 재리뷰한다.
   지적 없음도 검토 범위와 남은 한계를 기록한다. 검증되지 않은 영역을 통과로 쓰지 않는다.
5. fixture 테스트·타입 검사·빌드·CI와 task 범위 live E2E를 실행한다. 명령, UTC 또는 KST 시각,
   대상 SHA, 결과 수/해시/크기와 실패를 기록한다. 쿠키·키·storageState를 저장하지 않는다.
6. `docs/validation/<task>.md`와 PR 본문에 두 리뷰 결론·해결 내역·live/CI 결과를 넣는다.
   증빙 commit이 추가됐다면 검토한 소스 tree가 바뀌지 않았음을 확인한다.
7. 모든 게이트가 통과한 경우에만 Draft를 해제하고 PR head SHA를 확인해 머지한다.
   해당 task의 머지 확인 전 다음 구현 단계를 시작하지 않는다.

GitHub 계정 본인의 PR 승인 제한이 있어도 에이전트 리뷰 보고서는 유효한 독립 검토 증빙으로
보관할 수 있다. GitHub 승인이나 CI 성공을 실제 받지 않았으면 받았다고 기록하지 않는다.
